# 災害机上訓練シミュレーター 詳細実装計画

## 1. 実装方針

短時間で繰り返せるシングルモードを先に完成させ、そのゲーム状態と操作履歴を同じままマルチモードへ拡張する。画面を先に増やすのではなく、すべての操作をイベントとして記録し、そのイベントから現在状態、採点、振り返りを生成できる構造を中核にする。

## 2. 目標としないもの

- 実訓練の時刻進行をそのまま待つ長時間シナリオ。
- 診断名だけを当てるクイズ。
- 医学的に複数の妥当解がある判断の完全自動採点。
- 実患者情報や電子カルテとの接続。
- 初期段階での複雑な3D病院マップ。

## 3. ゲームの基本ループ

1. シナリオと難易度を選ぶ。
2. 初期病床・手術室・人員状況を確認する。
3. 患者が波状に来院する。
4. プレイヤーが情報を取得し、トリアージ、検査、処置、移動、部門連絡を行う。
5. 時間・場所・未実施項目に応じて患者状態と環境イベントが変化する。
6. 終了時に4軸スコア、患者転帰、滞留、連絡、操作タイムラインを振り返る。

## 4. 中核データモデル

### SessionConfig

- シナリオID、名称、30／45／60分の制限時間。
- 全50症例、圧縮後の投入オフセット、同時到着グループ。
- 初期容量、利用可能施設、音響設定、途中スコア表示設定。
- シングル／マルチ、参加者の役割。

### GameEvent

- 一意なイベントID。
- セッションID、連番、訓練時刻、実時刻。
- 操作者ID、役割、イベント種別。
- 患者ID、対象ゾーン、対象施設、入力内容。
- 自動イベントか手動操作か、訂正元イベントID。

最初に実装するイベント種別：

- `session_started`、`clock_started`、`clock_paused`、`time_advanced`
- `patient_arrived`、`patient_moved`
- `information_requested`、`information_revealed`
- `triage_submitted`
- `assessment_completed`、`test_ordered`、`test_completed`
- `patient_handoff_completed`
- `score_applied`、`penalty_applied`
- `session_ended`、`event_reverted`

### PatientRuntime

- 現在ゾーン、搬送先、搬送残時間。
- 患者役中／想定のみ。
- 開示済み情報の集合。
- 一次・二次トリアージのプレイヤー回答。
- 検査依頼、検査完了、処置、部門連絡、転帰。
- 最終評価時刻、ゾーン到着時刻、急変状態。

### ScoreState

- トリアージ、診療判断、患者フロー、部門連携の各点数。
- 対象患者、時刻、点数、理由を持つ明細。
- コントローラーによる手動加点・減点とコメント。

## 5. シナリオ構成

### 30分：高速

- 50症例すべてを使用する。
- 優先順位、患者滞留、情報整理を強く問う高密度モード。
- 経験者の反復訓練と、チームの処理能力確認に使用する。

### 45分：標準

- 50症例すべてを使用する。
- 救急車、乗用車、Walk-inの投入波、再評価、手術・ICU連絡を含む。
- 通常の机上シミュレーションの基本モードとする。

### 60分：検討重視

- 50症例すべてを使用する。
- 診療判断、部門連絡、コントローラーとの確認に時間を確保する。
- 初回実施や、振り返りを挟みながら進める訓練に使用する。

元の来院時刻の最初と最後を圧縮範囲として比例変換し、症例の順序、同時到着、乗用車同乗グループ、Walk-in投入波を維持する。開始直後の準備時間と終了前の整理時間は別枠として確保する。

## 6. 情報開示設計

| 情報 | 開示条件 | プレイヤー | コントローラー |
| --- | --- | --- | --- |
| 来院前情報 | 患者到着 | 表示 | 表示 |
| 一次所見 | 一次評価を実行 | 表示 | 表示 |
| 詳細バイタル | バイタル測定 | 表示 | 表示 |
| 診察所見 | 診察を実行 | 表示 | 表示 |
| 検査結果 | 検査依頼後、所要時間経過 | 表示 | 表示 |
| 追加イベント | 条件成立 | 表示 | 事前表示 |
| 想定治療・転帰 | 原則として終了後 | 非表示 | 表示 |
| 分岐・採点条件 | 常時非表示 | 非表示 | 表示 |

開示ボタンは「情報を見る」ではなく「一次評価」「バイタル測定」「診察」「検査依頼」のように、実際の行動として表現する。

## 7. 採点ルール

### トリアージ

- 一致：加点。
- 過大評価：小さな減点。
- 過小評価：大きな減点。
- 再評価で適切に変更：回復加点。
- 急変後も未評価：時間に応じた減点。

### 診療判断

- 症例DBのコントローラーチェックポイントをルール候補として使用。
- 必須処置の順序と時間窓を評価。
- 複数解がある項目はコントローラーが「妥当」「一部妥当」「不十分」を入力。

### 患者フロー

- 適切なゾーン移動、搬送完了、転帰確定を加点。
- 未評価・検査後・搬送後の放置、患者所在不一致を減点。
- 混雑そのものではなく、混雑への対応を評価。

### 部門連携

- 早期受入依頼、容量確認、定時報告、代替案提示を加点。
- 無承認入床、容量超過、連絡遅延、未確認情報の確定扱いを減点。

## 8. 画面構成

### 開始画面

- モード選択。
- シナリオカード（30／45／60分、全50症例、時間密度、難易度）。
- 初期資源設定と開始前確認。

### ゲーム画面

- 上部：時計、残時間、進行、接続状態、音響。
- 左～中央：病院フローマップと患者コマ。
- 右：患者情報と行動ボタン。
- 下部または通知領域：到着、急変、検査終了、受入回答。
- スコアは設定に応じて表示／非表示。

### コントローラー画面

- 予定イベント一覧。
- 手動イベント投入、保留、前倒し。
- 全患者情報、分岐条件、チェックポイント。
- 手動評価とメモ。

### 振り返り画面

- 4軸スコアと明細。
- 患者ごとの移動・評価・検査・連絡タイムライン。
- ゾーン別人数と最長滞留。
- 重要判断、見逃し、回復判断。
- JSON／CSV出力。

## 9. PWA・保存

- `vite-plugin-pwa`またはWorkboxでService Workerを生成する。
- アプリ本体、症例、シナリオ、アイコン、音声を事前キャッシュする。
- IndexedDBへセッション設定、イベント履歴、復元スナップショットを保存する。
- 新版のService Workerは進行中セッション終了後に適用する。
- Background Sync APIだけに依存せず、画面復帰時と接続回復時にも同期する。

## 10. マルチモード

- サーバーがセッション、参加者、役割、イベント連番の正本を持つ。
- クライアントは操作コマンドを送り、確定イベントを全端末へ配信する。
- 役割権限をサーバー側でも検証する。
- Supabase Realtime相当のBroadcast／Presenceと永続イベントテーブルを利用候補とする。
- 参加者表示、切断・復帰、観戦・投影専用を扱う。
- オフライン中のマルチ操作は「保留」と明示し、競合時は進行役が採否を決める。

## 11. 実装フェーズ

### Phase 1：ゲーム基盤

- [ ] 全50症例の投入順と30／45／60分プリセット。
- [ ] 元の投入間隔を圧縮し、同時到着グループを維持する変換処理。
- [ ] `GameEvent`とイベント追加処理。
- [ ] 患者移動、時刻操作、到着を履歴化。
- [ ] 4軸スコア明細と基本トリアージ採点。
- [ ] 最低限の滞留ペナルティ。

完了条件：短時間シナリオを開始し、操作・点数・理由が再読込後も残る。

### Phase 2：情報開示・分岐

- [ ] 一次評価、バイタル、診察、検査の行動ボタン。
- [ ] 開示済み情報の患者別管理。
- [ ] 検査所要時間と完了通知。
- [ ] 条件イベント、急変、再評価。
- [ ] 急変時の患者コマ色変更、文字ラベル、未対応時の脈動、対応開始表示。
- [ ] プレイヤー／コントローラー情報の分離。

完了条件：未取得情報が見えず、行動と時間経過により正しく開示される。

### Phase 3：診療・連携

- [ ] 処置選択とチェックポイント評価。
- [ ] 電話受入依頼、回答、理由、入床完了。
- [ ] 定時報告と本部判断。
- [ ] 軽症ゾーンの待ち列・診察室4室。
- [ ] 患者役終了と想定コマ切替。

完了条件：症例5、13、40、41、45の部門連携をシングルモードで再現できる。

### Phase 4：振り返り・音響・PWA

- [ ] 終了条件と振り返り画面。
- [ ] タイムライン、滞留、容量推移。
- [ ] BGM、環境音、通知音、字幕通知。
- [ ] IndexedDBとService Worker。
- [ ] オフライン、更新、クラッシュ復元試験。

完了条件：ネットワークなしで開始からレポート出力まで完走できる。

### Phase 5：マルチモード

- [ ] セッション作成、参加コード、役割選択。
- [ ] サーバーイベント正本、リアルタイム配信。
- [ ] 役割権限、競合、再接続。
- [ ] 投影専用・評価者画面。
- [ ] 5～10端末での負荷・切断試験。

完了条件：複数部門が同一セッションを操作し、状態・時計・履歴が一致する。

## 12. 実装順序上の注意

- マルチ同期を現在のReact stateへ直接足さない。イベント履歴を先に導入する。
- 採点値は画面コンポーネント内で計算せず、独立した純粋関数にする。
- 症例データと実行状態を分け、Notion由来データを書き換えない。
- プレイヤー向け情報は「隠すCSS」ではなく、ビューへ渡すデータ段階で除外する。
- 医学的な採点ルールは症例ごとに確認可能な設定として保持し、コードへ散在させない。
