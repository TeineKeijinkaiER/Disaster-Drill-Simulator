# 災害机上訓練シミュレーター 要件定義書

| 項目 | 内容 |
| --- | --- |
| 文書版 | 0.2 |
| 状態 | ゲーム化・マルチプレイ拡張方針反映 |
| 対象 | 2026年度 手稲渓仁会病院 災害訓練の事前机上訓練 |
| アプリ形態 | PC・タブレット向けWebアプリ / PWA |
| 基本運用 | シングルモード、進行役PC + 外部モニター |
| 拡張運用 | 複数端末による役割分担型マルチモード |

## 1. 目的

多数傷病者受入時の患者動線、トリアージ、診療場所の選択、電話連絡、
ER・EU・ICU・手術室の収容能力調整を、本番前に机上で反復訓練する。

本アプリは単一の正解経路を強制するゲームではない。参加者の判断、連絡、
患者の滞留、収容能力の変化を可視化し、訓練後に振り返れることを目的とする。
正確性、適時性、患者フロー、部門連携を複数軸で評価し、短時間でも判断と
振り返りを反復できる訓練ゲームとする。

実訓練の時刻をそのまま待つ長時間シナリオは設けない。使用症例50例はすべて
投入し、元の投入順と投入波を保ったまま30～60分へ圧縮して実施する。

## 2. 適用範囲

### 2.1 初版に含めるもの

- 2026年度使用症例50例の読込と時刻順投入
- 救急車、乗用車・徒歩、トリアージポスト、救外ゾーン、軽症ゾーン、EU、
  ICU、手術室を含む模式的な病院マップ
- ER重症・中等症ベッド、軽症診察室、EU・ICU病床、手術室の容量管理
- 患者役がいるコマと、患者役終了後の想定コマの識別
- 軽症ゾーンと救外ゾーン間の3分搬送
- 電話による受入依頼、承認、保留、拒否の記録
- 操作履歴、自動保存、終了後の振り返り
- オフライン運用
- 全50症例を使用する30分、45分、60分の時間圧縮シナリオ
- 段階的な患者情報の開示
- トリアージ、診療判断、患者フロー、部門連携の評価
- 患者滞留、容量超過、連絡遅延等のペナルティ
- 通知音、環境音、BGMの個別オン・オフ

### 2.2 初版に含めないもの

- 実際の病院建物や廊下の忠実な再現
- 電子カルテとの直接接続
- Notionとの常時同期
- 実患者の個人情報の保存
- 診断・治療内容を単一正解とする完全自動採点
- 実訓練の時刻進行をそのまま待つ長時間シナリオ

複数PC間のリアルタイム同期は段階的に実装する。シングルモードのゲーム状態、
操作履歴、採点、振り返りを先に完成させ、同じイベントモデルを利用して
マルチモードへ拡張する。

## 3. 利用者

| 利用者 | 主な操作 |
| --- | --- |
| 進行役 | シナリオ設定、時計操作、患者投入、イベント提示、電話応答、訂正 |
| プレイヤー | トリアージ、移動先、優先順位、受入依頼を口頭で判断 |
| 記録・評価者 | 判断経過、滞留、病床使用状況、未処理患者を確認 |
| 投映画面閲覧者 | 患者位置、搬送中、各ゾーンの混雑状況を確認 |
| 部門プレイヤー | 担当ゾーンの患者評価、処置、移動、受入依頼を操作 |

初版では進行役がプレイヤーの判断をアプリへ入力する。

## 3.1 ゲームモード

### シングルモード

- 1人の進行役が全ゾーンを操作する。
- 高速30分、標準45分、検討重視60分を基本プリセットとする。
- いずれのプリセットも50症例すべてを使用し、時間圧縮率のみを変更する。
- 投入順、同時到着グループ、主要な急変イベントの順序は実訓練資料に合わせる。
- 一時停止、早送り、任意イベント投入を可能にする。

### マルチモード

- 進行役がセッションを作成し、参加者は短い参加コードまたはQRコードで参加する。
- 進行役、トリアージ、救外、軽症、手術室・AG室、ICU・EU、本部、評価者、
  投影専用の役割を設定できる。
- 進行役端末が訓練時計とシナリオイベントの正本となる。
- 各端末には担当範囲と、その役割が正規の手順で入手した情報のみを表示する。
- 切断時は端末内に操作を保留し、再接続時に重複なく同期する。
- 同じ患者への競合操作は先着確定とし、後続端末へ理由付きで通知する。

## 4. 施設・資源

### 4.1 固定される最大容量

| 施設 | 最大容量 | 補足 |
| --- | ---: | --- |
| ER重症ベッド | 4床 | 主に赤・重症患者を配置 |
| ER中等症ベッド | 7床 | 主に黄・安定患者を配置 |
| 軽症ゾーン診察室 | 4室 | 同時診察は最大4例 |
| 軽症ゾーン待合 | 上限なし | 混雑数と待ち時間を表示 |
| 軽症二次トリアージ | 待合の一部 | 診察待ちとは別の待機列 |
| ICU | 16床 | 災害前患者数を設定可能 |
| EU | 30床 | 災害前患者数を設定可能 |
| 手術室 | 15室 | 一般使用14室、眼科専用1室 |

### 4.2 訓練開始時に変更できる項目

- ICU既存患者数、使用不能床数、退室可能床数
- EU既存患者数、使用不能床数、退院・転棟可能床数
- 手術室ごとの使用状況、進行中手術の終了予定時刻、スタッフ確保状況
- 使用可能な軽症診察室数（0～4室）
- ER重症・中等症ベッドの実患者占有数

各施設は「最大数、既存患者、災害患者、使用不能、空き」を表示する。

眼科専用手術室は、通常の災害症例へ自動割当しない。例外的な転用は進行役が
理由を入力して実施し、操作履歴へ残す。

## 5. 訓練全体の流れ

1. 進行役がシナリオと災害発生前の占有状況を設定する。
2. アプリが訓練時刻に従って患者を救急車または乗用車・徒歩に出現させる。
3. プレイヤーが一次トリアージと診療ゾーンを判断する。
4. 進行役が患者コマをトリアージポスト、救外、軽症へ移動する。
5. 救外または軽症で申し送りが完了した時点で患者役を終了できる。
6. 以後は電話連絡とホワイトボード上の想定患者として処理する。
7. 手術室、ICU、EU等への受入依頼と結果を記録する。
8. 終了後に患者移動、判断、滞留時間、容量推移を振り返る。

救急車症例は救急車搬入口から救外へ進むことを基本とするが、軽症ゾーンへの
誘導も許可する。想定トリアージ色や想定診療ゾーンと異なる判断を禁止せず、
差異を振り返り用に記録する。

### 5.1 短時間シナリオ

| 種別 | 標準時間 | 主な学習目標 |
| --- | ---: | --- |
| 高速 | 30分 | 全50例を高密度投入し、優先順位・滞留・情報整理を重視 |
| 標準 | 45分 | 全50例を投入し、トリアージと部門連携のバランスを重視 |
| 検討重視 | 60分 | 全50例を投入し、診療判断・再評価・連絡の検討時間を確保 |

- シナリオ時刻は実際の訓練要綱の時刻をそのまま待つのではなく、開始時刻を0分として圧縮する。
- 50症例はすべて使用し、元の来院時刻の間隔を選択時間へ比例圧縮する。
- 同時到着の症例、乗用車の同乗グループ、Walk-inの投入波は同時性を維持する。
- 同一シナリオでも初期病床、投入間隔、急変条件、追加イベントを変えて再実施できる。
- 進行役は予定イベントを保留、前倒し、取消、手動投入できる。

### 5.2 患者情報の段階的開示

#### 到着経路別の一次トリアージフロー

#### 症例DBの情報項目定義

- `症例設定・概要`：来院設定、受傷機転、病態、想定経過を統合して記載する。旧 `シナリオ想定` と旧 `症例概要` は使用しない。
- `一次トリアージ所見`：START法に沿った一次評価の観察事実のみを記載する。歩行可否、呼吸状態、循環状態、CRT延長、従命困難、意識などを含め、判定色・診療ゾーン・結果は記載しない。
- `来院後初回バイタル`：救外症例は診察室での初回バイタル、意識を含めて記載する。軽症症例は二次トリアージ時のバイタル、意識を含めて記載する。
- `診察所見`：バイタルおよび意識を除く診察所見のみを記載する。
- `救急隊バイタル`：救急車症例について、救急隊が測定した意識・バイタルを記載する。乗用車・徒歩症例は空欄とする。

- 救急車搬入口では、救急隊からの患者情報と救急隊測定バイタルを表示する。
- 救急車症例は搬入口で直ちにトリアージ区分を選択し、その後に診療ゾーンへドラッグアンドドロップで移動する。
- 乗用車・徒歩来院では、到着時に表示する情報を受傷機転、受傷部位、移動可否に限定する。
- 乗用車・徒歩来院は全例を一次トリアージへドラッグアンドドロップで移動し、到着した時点でSTART法の評価所見を開示する。
- 乗用車・徒歩来院はSTART法の所見を確認してトリアージ区分を選択した後、診療ゾーンへ移動する。
- 上記の順序を飛ばす移動は受け付けず、必要な次工程を画面上に通知する。

受入条件：

- 救急車症例では搬入口にいる間からトリアージ選択ボタンが表示される。
- 乗用車・徒歩症例では一次トリアージ到着前にSTART所見とトリアージ選択ボタンが表示されない。
- 乗用車・徒歩症例を一次トリアージへ移動するとSTART所見とトリアージ選択ボタンが表示される。
- 未判定の症例を診療ゾーンへ直接移動しようとすると移動せず、理由が通知される。

#### 救急治療方針

- ER・軽症診療ゾーンに到着した対象症例では、救急治療方針を選択できる。
- 選択肢には気道確保・挿管、末梢ルート確保、急速輸液、輸血、外科コール、アトロピン投与、アドレナリン投与、胸腔ドレーン留置、骨盤バインダー、緊急手術、TAEなどを含める。
- 症例ごとの必須治療をすべて選択した場合に初期治療完了と判定する。
- 不要な選択肢は実行せず、看護師の「それ今必要ですか？」というフィードバックを表示する。
- 緊急手術・TAEは画像確認前には実行せず、「画像確認しないで大丈夫ですか？」とフィードバックする。
- 高リスク症例では初療開始から症例ごとに設定した期限までに必須治療を完了できなければ、患者を急変状態へ移行させる。
- プレイヤー画面には想定トリアージ、想定治療、コントローラー指示などの答えとなる情報を表示しない。

患者詳細は最初から全項目を表示せず、プレイヤーの行動と患者の診療段階に応じて開示する。

1. 来院前：年齢・性別、主訴・受傷機転、救急隊または同乗者から得た情報。
2. 一次トリアージ：歩行、呼吸、循環、意識、一次判定に必要な所見。
3. 二次トリアージ・初療：詳細バイタル、診察所見。
4. 検査：検査を依頼し、所要時間が経過した後に検査結果。
5. 処置：プレイヤーが処置を宣言した後の反応・状態変化。
6. 条件イベント：時間、未処置、再評価、場所等の条件成立後に追加イベント。

- 情報取得操作は履歴へ記録し、取得時刻を採点に利用する。
- プレイヤー画面に想定転帰、正解診療ゾーン、コントローラー指示、分岐条件を表示しない。
- コントローラー画面は全情報とイベント条件を確認できる。
- 投映画面は患者位置、混雑、時計を中心とし、医学的な正解情報を表示しない。

## 6. 軽症ゾーンの流れ

軽症ゾーンは一般外来として扱い、次の状態を個別に管理する。

1. 軽症ゾーン受付
2. 二次トリアージ待ち
3. 二次トリアージ中
4. 診察待合
5. 診察室1～4
6. 処置・検査待ち
7. 帰宅、入院、救外移動等の転帰待ち

待合人数に機械的な上限は設けない。ただし、待機人数、最長待ち時間、
二次トリアージ未実施数を常時表示する。

## 7. 患者コマ

### 7.1 表示項目

- 症例IDと短い症例名
- 年齢区分
- 来院時刻・来院方法
- 現在のトリアージ色
- 現在位置と状態
- 患者役の状態
- 待ち時間
- 手術、ICU、EU等の依頼状況

### 7.2 視覚表現

- トリアージ区分はコマ上部の赤・黄・緑の帯で示す。
- 患者役がいるコマは白背景、人物アイコン、「実役中」ラベルで示す。
- 患者役終了後は青灰色背景、電話アイコン、「想定」ラベルで示す。
- 色だけに依存せず、アイコンと文字を必ず併用する。
- 選択中、搬送中、受入保留、容量超過を別の表示で示す。
- 急変時はトリアージ帯を保持したまま、患者コマ全体の背景・枠色を黄または赤へ変更し、「急変」と文字表示する。
- 未対応の重篤急変は脈動表示し、再評価後は「対応中」表示へ切り替えて脈動を停止する。
- 動きを減らすOS設定では脈動を使用せず、色・枠・文字だけで同じ状態を示す。

### 7.3 患者役の終了

救外または軽症ゾーンへ到着しただけでは自動終了しない。進行役が
「申し送り完了・患者役終了」を実行した時点で想定コマへ切り替える。
切替は取り消し可能とし、時刻を履歴に残す。

## 8. 移動と時間

### 8.1 軽症・救外間搬送

- 軽症ゾーンと救外ゾーン間の移動時間は両方向とも3分とする。
- 移動開始後は患者を「ストレッチャー搬送中」エリアへ表示する。
- 搬送中は出発地にも到着地にも収容されていないものとして扱う。
- 残り時間を表示し、3分経過時に到着通知を出す。
- 進行役は安全上・運営上の理由で搬送を中止または即時到着に訂正できる。
- 実役中・想定のいずれでも3分の移動時間を適用する。

ストレッチャー台数による同時搬送制限は、台数確定まで初版の必須要件に
含めない。搬送履歴は将来の制限追加に対応できる形式で保存する。

### 8.2 訓練時計

- 開始、一時停止、再開、指定時刻への移動を進行役が操作できる。
- 通常速度と早送りを用意する。
- 一時停止中は来院、搬送、手術終了等のタイマーも停止する。
- 時刻変更は履歴に残す。

## 9. 受入依頼と容量管理

救外・軽症から手術室、ICU、EUへ電話連絡を行った想定で、次を記録する。

- 依頼元、依頼先、患者、依頼時刻、依頼内容
- 回答状態：未連絡、応答待ち、承認、保留、拒否、取消
- 回答時刻、理由、追加条件

承認だけでは病床・部屋を消費せず、「入室・入床完了」で使用中にする。
空きがない施設へも依頼は可能だが、警告を表示し、容量を超えて黙って配置
してはならない。

一般病床、帰宅、転院等は初版ではマップ外の転帰として記録する。一般病床の
容量管理は、病床数が確定した後の追加機能とする。

## 9.1 採点

採点は単一の総合点だけでなく、次の4軸を個別に保持する。

| 評価軸 | 主な評価対象 |
| --- | --- |
| トリアージ | 一次・二次判定、過小評価、過大評価、再評価の適時性 |
| 診療判断 | 必要な評価・検査・処置・専門部門への連絡 |
| 患者フロー | 滞留時間、適切なゾーン移動、転帰確定、容量管理 |
| 部門連携 | 受入依頼、定時報告、患者一覧更新、資源不足の共有 |

- 過小トリアージは過大トリアージより大きな減点とする。
- 医学的に複数の妥当解がある項目は、ルールによる自動評価とコントローラー判定を併用する。
- 現在点は進行中に表示するか、終了まで隠すかをシナリオ設定で選べる。
- 終了後は点数だけでなく、加点・減点の時刻、対象患者、理由を表示する。

## 9.2 ペナルティ

- 赤患者の未評価時間超過。
- 二次トリアージ、診察、検査終了後、搬送後の放置。
- 急変条件成立後の再評価遅延。
- 受入承認なしの入室・入床、容量超過。
- 患者一覧と実際の所在・転帰の不一致。
- 手術、AG室、ICU候補の連絡遅延。
- 同乗者・車内残存者の見落とし。
- 余震後の安全確認を行わない診療継続。

混雑や満床そのものは減点しない。混雑を認識し、応援要請、優先順位変更、
代替病床、転院検討等の対応を行ったかを評価する。

## 10. 画面要件

### 10.1 初期設定画面

- シナリオ選択
- ICU、EU、ER、軽症診察室、手術室の初期状況設定
- 難易度プリセットと個別設定
- 設定内容の保存、読込、開始前確認

### 10.2 進行役画面

- 病院模式図
- 未到着、到着、各ゾーン、搬送中、転帰済みの患者一覧
- 訓練時計と次の予定イベント
- 患者詳細、想定情報、追加イベント、コントローラー指示
- 電話連絡と受入回答
- 取り消し、訂正、メモ

### 10.3 投映画面

- 病院模式図、患者位置、搬送中、混雑状況
- 各施設の空き状況
- 訓練時計
- 症例の正解転帰、追加イベント、コントローラー指示は表示しない。

### 10.4 振り返り画面

- 患者ごとの移動タイムライン
- ゾーン別患者数と最大滞留数
- 受付、二次トリアージ、診察、受入依頼の待ち時間
- ICU、EU、手術室、ERの使用状況推移
- 想定と異なった判断の一覧
- 操作履歴のJSONまたはCSV出力

### 10.5 音響

- 平常、災害モード、患者集中、余震後の環境音またはBGMを用意できる。
- 救急車到着、急変、検査終了、受入回答、時間警告には短い通知音を使用できる。
- BGM、環境音、通知音は個別にオン・オフと音量調整ができる。
- 音声がなくても同じ情報を画面通知で認識できる。
- 実際の医療機器アラームと誤認しにくい音を用いる。
- 音声開始はユーザーの「訓練開始」操作後とし、ブラウザの自動再生制限に対応する。

## 11. データ要件

### 11.1 症例データ

Notionの使用症例DBを医学的内容の原本とする。アプリは個人情報を含まない
訓練用JSONまたはCSVを読み込む。最低限、次を保持する。

- 症例ID、症例名、年齢・性別設定
- 来院時刻、来院方法
- 想定トリアージ、想定診療ゾーン
- バイタル、所見、検査結果
- 想定治療、OPE・AG、想定転帰
- 追加イベント、イベント発生条件
- コントローラー指示、重点訓練ポイント

### 11.2 セッションデータ

- 初期設定
- 現在時刻と進行状態
- 患者の現在位置・状態
- 受入依頼と回答
- 施設占有状況
- 全操作履歴
- 進行役メモ

ブラウザ内へ自動保存し、再読込後に直前のセッションを復元できるようにする。
セッションはファイルとして書き出し・読込できるようにする。

## 13. 非機能要件

### 13.1 可用性

- 初回読込後はインターネット接続なしで全必須機能を使用できる。
- 操作ごとに自動保存し、ブラウザ異常終了後も直近状態を復元できる。
- 新版適用前に進行中セッションがある場合は警告する。
- オフライン時もシングルモードの開始、終了、採点、振り返りができる。
- マルチモードの通信切断時は状態を失わず、再接続状態を明示する。

### 13.2 操作性

- 1920×1080の進行役PCと外部モニターを主対象とする。
- 主要操作は2回以内のクリックまたはドラッグで完了できる。
- タブレットではドラッグ操作の代わりに「移動先を選ぶ」操作も提供する。
- 患者コマの文字が重ならず、50例投入時も一覧から検索できる。
- 誤操作を防ぐため、患者役終了、転帰確定、セッション終了は確認を求める。

### 13.3 性能

- 50症例と全操作履歴を保持した状態で、主要操作結果を1秒以内に表示する。
- 搬送・来院タイマーの画面上のずれは通常運用で1秒以内とする。

### 13.4 セキュリティ・情報管理

- 実患者情報を入力しない。
- 初版はデータを外部サーバーへ送信しない。
- 公開リポジトリへ認証情報、個人情報、非公開の連絡先を保存しない。
- マルチモードではセッション単位の参加権限と役割権限を適用する。
- セッションには訓練用の仮名・症例IDのみを保存する。

## 14. 受入条件

- [ ] ER重症4床、中等症7床を別々に管理できる。
- [ ] ICU16床、EU30床の初期占有数を設定し、空床数が正しく計算される。
- [ ] 手術室15室のうち眼科専用1室が一般症例へ自動割当されない。
- [ ] 軽症診察室へ同時に5例目を配置しようとすると待合への誘導が提示される。
- [ ] 二次トリアージ待ちと診察待ちが別々に表示される。
- [ ] 軽症から救外へ移動すると3分間「搬送中」になり、経過後に到着する。
- [ ] 救外から軽症への移動にも同じ3分が適用される。
- [ ] 搬送中に時計を停止すると残り時間も停止する。
- [ ] トリアージ色と患者役状態を色、アイコン、文字で区別できる。
- [ ] 申し送り完了操作で患者役終了後の表示へ変わり、取り消せる。
- [ ] 容量を超える入床・入室を黙って確定できない。
- [ ] プレイヤーが想定と異なる診療ゾーンを選択しても操作を続行できる。
- [ ] 投映画面に正解転帰やコントローラー指示が表示されない。
- [ ] ページを再読込しても進行中セッションを復元できる。
- [ ] 通信を切断しても訓練を開始・継続・終了できる。
- [ ] 終了後に患者移動と受入依頼の時系列を確認できる。
- [ ] 30分、45分、60分の各プリセットで全50症例が投入される。
- [ ] 元の投入順、同時到着グループ、主要イベント順序が圧縮後も維持される。
- [ ] 未取得の検査結果・追加イベント・想定転帰がプレイヤー画面に表示されない。
- [ ] 情報を取得した操作と時刻が履歴へ残る。
- [ ] 過小トリアージ、長時間滞留、連絡遅延が理由付きで採点へ反映される。
- [ ] 現在点を非表示にしたまま終了後レポートで確認できる。
- [ ] 音響を完全に無効化しても画面通知だけで訓練できる。
- [ ] 急変症例のコマが黄または赤へ変化し、「急変」が文字でも表示される。
- [ ] 急変患者を再評価すると「対応中」に変わり、操作時刻が履歴と採点へ残る。

## 15. 技術方針

- React、TypeScriptを使用する。
- 静的Webアプリとしてビルドし、GitHub Pagesで公開可能にする。
- PWAとしてインストール可能にし、画面資材を端末へキャッシュする。
- セッション保存にはIndexedDBを使用する。
- アプリ状態はイベント履歴から再現可能な構造にする。
- 病院マップはSVGの実間取りではなく、レスポンシブな模式図として構築する。
- シングルモードはバックエンドなしで完結する。
- マルチモードはサーバー側のセッション正本とリアルタイム配信を使用する。
- マルチモードの操作は一意なイベントIDと連番を持ち、重複適用を防ぐ。
- 端末内の未同期操作はIndexedDBへ保存し、アプリ起動中に再送する。
- Background Sync APIのみに依存せず、復帰・再接続時にも同期処理を行う。
